# 批次共享预读与有序分段批量派单

## 范围

基于 Vercel daily-demo 的 `main@946d7cc9a8fc2d69f37c0ec53527104f4cc88e8c`，不涉及 FaaS、Skill 或生产数据库迁移。

目标是去除 20 条卡片中重复的全表定位和历史锚点扫描。`3 秒` 是正常路径预读 P95 的待实测目标，不是超时阈值，也不是已达成的生产 SLA。

## 实现

1. 每个 spreadsheet / sheet / 字段配置构成一个只属于当前 claim 的观察组。最多三个组并行读取。
2. 每组只解析一次 wiki token、元数据和必要表头，通过一次 `values_batch_get` 读取需求 ID、日期、负责人及可选项目列。各列按 5000 行切片，仍保留 20000 物理行上限。
3. 完整需求 ID 列建立唯一定位映射，不信任旧卡行号；重复或缺失 ID 被拒绝。读取响应数量、范围、顺序及已提供的 revision 必须一致。
4. 同一批次共用一次数据库 state + ledger 快照；保留原有锚点判定。计算每个目标时只观察目标及其之前的表格行，后面的人工行不能反向影响前面的分配。
5. 写入前先复核最早相关锚点至待处理目标的窗口。没有历史锚点时复核完整前缀，不假设短窗口已经完整。表格变化或外部 CAS 状态变化会使共享观察失效并完整重读。
6. 同表、同方向、同 scope 的空白连续片段使用一次带 CAS 的 `assignBatch` 和一次批量写入。人工行或不同锚点是片段边界，不能跨过去一起分配。
7. 决定落库后、写入前再次批量读取目标需求 ID 和负责人；位置变化或人工不同值使整段零写入并停止后续分配。已是同一负责人则只确认，不覆盖。
8. 写入后批量回读，只有需求 ID、负责人全部匹配才记成功。写接口响应丢失但回读全部证实成功时，只补记成功，不再次写入。
9. 只有已远端确认的本轮写入事实才更新本 claim 内的观察。其他回调不能使用该观察；没有实例级表格数据缓存。
10. RPC 回执未知、写入未确认或目标变化且决定已提交时停止后续片段，保留账本，明确要求对账。不将错误兜底为无条件逐条覆盖或新批次重派。

人工校准证据绑定锚点行、姓名和决定版本，不仅按姓名去重。同一姓名出现在不同人工行且其间有自动分配时，必须重新校准。

## 兼容与边界

- 当前分段快速路径限定单观察组、同方向，scope 为 `default/ad_review/ad_game`，方向为 `forward/reverse`。应急方向、隔离 scope 和混合方向仍走原有逐条安全引擎；其初始预读可共享，但不宣称它们全部进入批量写入。
- 缺少新能力的测试或兼容客户端保留原路径。
- 沿用同 batch ID、fingerprint、持久 claim、CAS 和成功项跳过规则。不会修改按钮里的原始 row_index 来改变批次身份。
- GET 和飞书批量写入不是跨系统原子事务。本改动缩短窗口并检查、回读，但没有消除任意时刻人工直改或移动行的竞争窗口；严格保证仍需要受控写入口/负责人列权限治理。
- 240 秒预算和 30 秒启动预留不变。慢读耗尽预算时，在新分段开始前保存并暂停。此项没有新增自动续跑队列；仍使用原批次的已有继续处理入口。
- 决定已提交而表格未确认时，现有批次状态协议仍显示 FAILED/PARTIAL，并写明“本段结果需对账”；不能据此断言决定已回滚或原表格没有写入。

## 本地验证

新增 `tests/batchSharedPreflight.test.js` 29 项。使用真实 LarkClient 适配层和严格 CAS 内存存储，所有外部系统均为本地 stub。

覆盖：

- 15013 行、20 个目标：完整共享扫描、一次批量分配、一次写入；
- 正序、倒序、中间人工行、同名不同人工锚点、全人工行；
- AD 实际 B/C/J 列、ad_review scope；
- 行移动、空旧行号、重复 ID、名单外人工值；
- 真实 CAS 冲突、持续冲突有界退出；
- 决定提交后人工填写或行移动时零批量写入；
- RPC 回执丢失、批量写响应丢失、部分写入/确认失败；
- 批次暂停后原身份恢复，已完成片段不重复分配；
- 并发重复点击、数据库快照不可用、超出扫描上限；
- 缺范围、乱序响应、混合 revision、单次表头解析。

同一 15013 行 / 20 条夹具比较：

| 指标 | 旧路径 | 新路径 |
| --- | ---: | ---: |
| 飞书 HTTP 调用数（整轮，不含数据库和 UI mock） | 405 | 8 |
| 需求/历史全扫描 | 每条分别执行 | 一次共享 |
| 正常全空批次分配 RPC | 1 | 1 |
| 正常全空批次写请求 | 1 | 1 |
| 写前目标身份及负责人复核 | 原快速路径缺少落账后复核 | 有 |
| 写后批量事实确认 | 原快速路径未做 | 有 |

上述是本地夹具中的调用数量证据，不是线上延迟测量。旧卡需要自动识别需求 ID 表头时会额外增加一次读表头。没有历史锚点、并发变化、多个片段时也会增加请求。

最终回归：928/928；新增定向：29/29；ESLint、Vite build、git diff --check 通过。全量 HTTP 模拟用例需要允许 127.0.0.1 回环连接；沙箱拒绝回环时不应把 EACCES 误判为业务回归。

## 发布前验收

不得拿当前未完成生产批次充当性能测试或自动补偿。

1. 在隔离表和测试群验证 20 空行、首/中/末人工值和多段场景；至少一组采用真实 AD B/C/J 列。
2. 分开记录冷/热环境的 `batch_preflight`（`refreshed_sheets=true`）以及 `batch_segment_success` 耗时；3 秒目标针对预读，不能用回调 HTTP 200 的耗时代替。
3. 真实飞书 API 必须接受返回范围和 revision 契约；检查需求定位、目标保护、写后回读与最终名单/游标。
4. 验证同批重复点击仅一组副作用、表格中途变更会重新观察或停止、写响应丢失只对账。
5. 只有这些隔离验收完成后才审批生产发布。线上 3 秒 P95 需真实样本，不得用本地 CPU 毫秒数或调用次数宣称通过。

本变更无数据库 migration、无生产环境变量改动、无新增 Vercel Function。回滚部署到此前的 main 即可恢复旧算法；持久成功记录、原 batch ID 和账本都必须保留，不可删除重建。
