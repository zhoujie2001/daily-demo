# 派单锚点一致性修复

基线：PR #109 / `0fe385d834756f9d3e91530a766e25aafa156185`。

## 修复范围

1. 自动派单账本记录已消费对应游标，后续读取不能把负责人名字重新解释为下一圈校准指令。只有最新有效的表格人工差异允许自动校准；已完成的指定负责人流程本身已经显式校准。
2. 校准和分配的 CAS 冲突均废弃原决策，重新读取名单、游标、账本、表格锚点、目标单元格和已有派单。禁止“旧锚点 + 新 CAS 版本”重试。目标行冲突后变为已填写时，只回读，不再派单或覆盖。
3. Supabase 使用一次只读 PostgREST FK embedding 同时读取 daily state 与 assignments。关系固定为 `bess_dispatch_assignments_day_scope_fkey`，按 `day_key + scope` 隔离，不新增 RPC 或重载。
4. 缺少快照接口的旧存储采用有界的前后版本验证，最多三次。持续变化时返回 `ASSIGNMENT_CONFLICT`，不继续使用混合快照。快照接口失败不会退化为不安全的并行读取。
5. 混合方向只消费一次人工锚点，之后沿用数据库游标；同一表格行存在多条账本记录时以最新记录为准。
6. 批次预读仅用于锚点规划，不再证明后续目标行仍为空。每一项执行前单独读取负责人格；与预读不一致时重新取得完整决策快照，再次核验该目标格。CAS 冲突会同时废弃全部待处理行的预读和方向锚点，而非只刷新当前行。
7. 自动派单落库后、PUT 写表前再次读取目标格。发现其他负责人则拒绝覆盖；已是预期负责人则不重复 PUT。读取失败或响应结构不完整同样禁止写表。正常空行新增两次单格 GET，只有变化或冲突才重新扫描完整锚点，避免对每行全表扫描。
8. 写前发现人工变化而派单已经落库时，保留账本和人工表格值，报告待人工核对；重试发现表格与账本不一致仍失败，不回滚游标、不重新派单，也不伪报成功。
9. 单条 `p1Dispatch` 的自动派单和名单表单提交也传入 `requireEmpty: true`。提交后拒写或写回无法确认时，不发送成功结果卡、不执行成功按钮更新、不把 pending 标记完成；提示账本已落库且需要核对。单条与批次共用表格/账本匹配检查，重试遇到人工值与原派单不一致时返回 `SHEET_ASSIGNMENT_MISMATCH`，而非把人工值伪装为原派单成功结果。

## 安全边界

- 无数据库迁移，无 schema、RLS、ACL、RPC 签名修改。
- 不删除或清空生产记录，不重派、不发卡、不重放已补偿的 `816892/816912`。
- 不更改环境变量、Skill、网络出口或现有生产部署。
- 本修复针对锚点与 CAS 决策一致性，不声称解决跨系统事务原子性或代理网络不可用。
- 表格没有可信编辑时间；人工差异仍按现有“最高有效行”规则选择，不能据此声称恢复真实人工修改时间顺序。
- 写前 GET 与 PUT 仍不是飞书表格原子 CAS。本次阻止已观测到的人工值被旧快照覆盖，但不能保证最后一次 GET 返回后、PUT 生效前的人工编辑绝不被覆盖。若要求任意并发时刻的严格保证，需要经授权将自动写入列设为单写者、人工修改走同一受控入口，或采用经确认支持条件写入的接口；本 PR 不擅自修改表格权限或业务操作方式。
- 写前空值保护用于批次与单条自动派单（含名单表单提交）。指定负责人流程的既有显式修改语义未改动，不声称该流程也具备只写空格保护。
